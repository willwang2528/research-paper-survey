# 带证据的自迭代与版本管理

当前版本见仓库 VERSION、skill 内 VERSION 和 SKILL.md metadata。自迭代指持续记录运行反馈、形成可检验改进并发布新版本；不是脚本自动重写自身、自动放宽纳入标准或自动推送。用户要求研究 SOP 时，应以这些记录开展方法研究。

## 版本对象

区分三个对象：skill 发布版本、数据 schema_version、单次调研协议版本。

- 发布版本：仓库 `VERSION`、skill 内 `VERSION`、SKILL metadata.version、CHANGELOG 对齐；发布用相同版本 Git tag。reference 不硬编码“当前版本”，避免发布后失配。
- schema_version：运行文件结构发生不兼容变化时提升，并提供迁移说明/工具。不能用升 skill 版本掩盖旧数据读不懂的问题。
- 协议版本：某调研问题的条件或范围变化，记录在该 run 的协议修订记录；不必因此升级通用 skill。

采用 SemVer：PATCH 修复兼容 bug/文字错误；MINOR 增加兼容能力或显著流程改进；MAJOR 引入不兼容接口/方法契约。0.x 仍应明确写出破坏性变化，不把“开发中”当作静默改动许可。版本只表达变更，不证明效果提升。

## 每次运行的闭环

1. 记录观察：发生在哪个 run、query、work 或命令；期望与实际是什么；来源和日志在哪里。
2. 分类反馈：retrieval、screening、evidence、coverage、learning、tooling、security 或其他明确分类。
3. 提出假设：改哪一步、为何能改善、可能带来什么代价。区别事实观察与推测。
4. 写入 `feedback.jsonl`；必要时在 run 内补 `iteration-notes.md`。不把未验证提案写成已发布能力。
5. 维护者定期汇总重现问题，在 `candidate/<topic>` 分支实现。分支名为建议，不是自动发布指令。
6. 运行回归与方法评估，比较相同输入上的基线和候选；记录失败、成本及边界。
7. 更新契约、模板、帮助、测试、VERSION、SKILL metadata 和 CHANGELOG；审查无凭据或私有运行数据。
8. 按当前用户授权提交/推送/发布。没有发布授权时交付可审查 diff，不自行公开数据。

## 仓库维护命令

这些命令在完整仓库中可用；仅安装 skill 目录时需回到原仓库维护。`<repo>` 为仓库根，iteration ID 使用小写字母、数字、连字符，下面版本号必须换成大于当前版本的目标版本。

```sh
python3 <repo>/scripts/evolve.py new --id scope-review-gate --problem "协议修改后旧验收可能被误用" --proposal "将评审和覆盖证据绑定当前协议指纹"
python3 <repo>/scripts/evolve.py check --id scope-review-gate
python3 <repo>/scripts/evolve.py release --id scope-review-gate --version <next-version> --summary "记录具体变化与旧运行迁移要求"
```

new 写 `iterations/<id>/plan.json`，不实施提案。check 执行 unittest 回归，保存 tests.txt/check.json，检查三处版本一致，记录源码摘要及测试期间是否变化。check 之后修改源码需要重新 check。release 仅在最近检查通过且源码摘要未改变时更新两处 VERSION、SKILL metadata 和 CHANGELOG，并留下 release.json；同一 iteration 不能重复发布，不自动 commit/tag/push/install。

回归通过不证明真实研究质量提升。方法效果仍需补独立种子/标注集、原文支持、成本等研究证据。脚本不会自动评判该证据的科学充分性。

## 指纹门禁的迁移说明

从 0.1.x 运行记录迁移到 0.2.0 的新增字段属于 schema 1 的加法扩展，但验收要求更严格：所有 review 需要 scope_fingerprint，coverage 需要 protocol_fingerprint。旧文件可读取不代表旧验收可直接复用。

先对旧 run 运行 prepare，不覆盖原评审；根据当前需求重核 core/background/excluded/pending，更新相应证据与范围指纹；按完整协议重核覆盖并更新协议指纹。缺全文、未确定的条件继续 pending。查询指纹包含工具版本，升级后按 audit 提示重新执行当前计划查询。禁止只复制新 hash 使旧记录通过。

## 可检验的评估维度

0.2.2 是兼容的流程说明修订：按任务选择渠道，细化会议近几届目录浏览与人工覆盖记录；未新增 provider、自动浏览能力或数据字段，旧运行无需数据迁移。升级后的查询指纹仍包含新工具版本，若要继续旧 run，按 audit 提示重跑查询并真实复核受影响覆盖，不修改历史报告冒充已执行新流程。

| 维度 | 可操作指标 | 必须保留的边界 |
|---|---|---|
| 检索覆盖 | 已知相关种子命中数/种子总数 | 不是未知全领域召回率；区分调参种子与留出种子 |
| 筛选质量 | 研究者标注集上的符合/误纳/漏纳及分歧 | 标签来源、对象、样本量与一致性要记录 |
| 主张证据 | 关键主张中能由原文直接或有条件支持的比例 | 链接可解析或字段非空不是支持关系 |
| 结构可靠性 | 无效 core 被拒绝、日期/版本/缺字段检查通过率 | 只衡量门禁，不证明科学事实 |
| 去重质量 | 精确 ID 重复、不同版本、冲突记录的误合并/漏合并 | 标题相似度不是 gold label |
| 成本 | API 次数、时间、候选数、人工全文时间 | 效率提升需同时报告质量是否下降 |
| 学习效果 | 能否解释问题/机制/取舍/证据边界 | 生成笔记长度不是掌握程度 |

当建立正式 benchmark 时，记录数据许可、标注规则、领域分布、时间窗口、评价者和预先定义的指标。用真实研究者判断和原文对照；另一个 LLM 可辅助复核，但不能成为唯一真值。

## 最小回归清单

- API 成功、空结果、分页/截断、限流、鉴权失败和网络错误可区分。
- key 不出现在日志、报错、URL、raw 响应或公共夹具里；用合成哨兵 token 测试，不用真实 key。
- DOI/arXiv 精确重复正确归并，缺 ID/冲突/相似标题不错误合并。
- 未读全文、身份未知、硬条件 no/unclear、日期不符、缺证据都不能获得已核验 core。
- 缺 review、重复 review、孤立 work_id、覆盖 pending/blocked、查询失败不能被静默当完整结果。
- 非 strict 草稿如实显示缺口；strict 行为与文档一致。
- 旧版本夹具能读，或提供明确迁移路径；生成报告可对账。

仅文档措辞变化无需机械新增镜像测试；修改到判定、网络、去重或安全边界时要有行为测试。网络 smoke 验证接口可访问，不是调研有效性实验。动态 API 比较需保存原始响应，避免把数据库变化当方法收益。

## 一次迭代记录模板

```text
候选版本 / 基线 commit：
问题与受影响 run：
直接证据（query/work/log/原文位置）：
改进假设与可能代价：
修改范围：
评估数据与标签来源：
回归结果：
方法评估结果（分母、条件、成本）：
是否触及 schema / 迁移方式：
仍未解决的限制：
决定：发布 / 继续实验 / 放弃
决定理由、核验者和日期：
```

出现实际回归时可回退对应 commit 或 release；旧 run 保留原版本和事实记录。不要直接改旧报告，让它看起来一直采用新方法。

## 0.2.3 展示模板迁移

新增逐篇介绍的固定开头及元数据核验规则；不改变检索、纳入门槛或 schema。旧报告保留原样，再次交付时核对最新元数据后采用新模板。CLI 报告仍为审计草稿，不自动抓取单位、CCF 或最新版本。若升级后继续运行旧 run，查询指纹仍含工具版本，按 audit 提示处理，不能只修改历史指纹。

## 0.2.4 精简开头展示

兼容展示修订：删除首行冗余字段标签及英文单位对照，中文题名单列，会议后直接接年月；版本号在 URL 中表达，日期口径留在收录证据记录。摘要、来源核验与 CCF 边界保留。无 schema 或脚本行为变化，旧报告不自动改写；旧 run 继续执行时仍按 audit 处理含工具版本的查询指纹。

## 0.2.6 单位语言与信息顺序

替代0.2.4的单位仅中文规则：中国机构中文、其他机构英文，不再因缺中文译名丢失已知英文署名。中文题名提前，作者单位单列，摘要仍在URL后。仅展示契约变化，无schema迁移，旧报告不自动改写。
